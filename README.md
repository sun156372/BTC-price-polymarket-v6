## 二、问题 1：频率差 9 倍 —— 是测量错误，不是市场变化

你截图里的数据：217 个窗口，只成交 6 笔（2.8%）。回测预期约 18%。各闸门分布：

```
105  (48.4%)  signal:below_threshold         回测约 27%
 52  (24.0%)  imbalance:book_not_lopsided    回测约 41% 通过
 52  (24.0%)  deviation:spot_move_too_small  回测约 90% 通过
  6  ( 2.8%)  ready
  2  ( 0.9%)  signal:missing_quote
```

**每一道闸门都在过度拒绝。** 根因是**V4 的测量方式**：

**每个闸门都在比较"开盘值"和"决策值"的差**：
* 方向闸门：`up_mid_now − up_mid_open`
* 现货闸门：`spot_now / spot_open − 1`
* 失衡闸门：决策瞬间的失衡

V4 的实现有三个测量缺陷：

1. **单循环轮询**：每次迭代要发市场查询 + 现货查询 + 2 个盘口请求，实际周期约
   **2 秒**，不是代码里写的 1 秒。
2. **开盘价记录太晚**：只在"窗口开始后 20 秒内恰好轮到"时才记录开盘中间价。
   **开盘价记录晚了，所有差值都被压缩，三道闸门同时过度拒绝。**
3. **现货按"最后一次取到的值"使用**，而不是按时间戳精确配对。

**V6 的修复**：

| 修复 | 做法 |
|---|---|
| 现货连续采样 | `SpotTracker` 独立线程每 0.25s 采样，保留完整序列 |
| 开盘价尽早记录 | 窗口一开就记录，并**报告实际滞后了多少秒** |
| 精确命中决策时刻 | 用短睡眠逼近目标秒，而不是粗轮询 |
| **记录每个闸门的测量值** | 不只记拒绝原因，而是记录每个窗口的每个测量量 |

最后一条是关键：**V4 无法回答"到底是哪个闸门在拒绝"，V6 可以直接对比分布。**

会话结束时 V6 打印实时分布与回测参考的并排对比：

```
  |imbalance|  p10 ...  median ...  p90 ...    回测: median 0.154, >=0.30 占 29.0%
```

**如果实时分布明显低于回测参考，那就是测量不匹配，不是市场变了。**

## 三、问题 3：深度 —— 结论和我的假设相反

**我原先的假设是错的，需要更正。**

我原本以为：数据集有完整深度，实时接口只给前 10 档 → 实时失衡被压缩。

**实测结果相反：**

| | 档位 | 依据 |
|---|---|---|
| **研究数据集** | **最多 10 档/边，82% 的采样正好卡在 10 档** | 本地实测 649,545 个盘口快照 |
| **实时 CLOB 接口** | **文档称返回"完整订单簿、所有档位"，且没有任何 depth 参数** | 官方文档镜像 + 官方 SDK 源码 |

**所以被截断的是数据集，不是实时接口。** 这意味着：

> **V4 的实时循环拿"完整深度"算失衡，去比一个用"前 10 档"拟合出来的 0.30 阈值
> —— 这两者不是同一个量。**

失衡是比率，**更深的盘口会把比率拉向 0**（远离盘口的档位稀释了盘口附近的倾斜度）。
所以实时算出的 `|imbalance|` 系统性地更小，**同一个 0.30 就拒绝得多得多**。
这正好解释了问题 1 里失衡闸门 41% vs 90% 的差距。

### 能不能拿到完整深度？

**能，而且比数据集更全：**

| 方式 | 说明 |
|---|---|
| `GET /book?token_id=` | 文档称完整盘口，无限档参数 |
| `POST /books` | 批量，最多 500 个代币，体量更省 |
| **WebSocket** `wss://ws-subscriptions-clob.polymarket.com/ws/market` | 订阅时推送**完整盘口快照**，之后推 `price_change` 增量（`size:"0"` = 删除该档）。**官方推荐用它替代轮询** |

### V6 的处理：不假设，而是测量

`engine_v6/feed.py` 把档位明确参数化（`DATASET_DEPTH = 10`，即阈值所对应的定义），
并且 `recorder` 在**每次决策时同时记录 5/10/20/全盘口四个口径的失衡**：

```python
DEPTH_PROBES = (5, 10, 20, None)
```

**`tools_v6/depth_check.py` 会在你的交易机器上把两边并排打印，并给出判定。**

### 附带发现（也是实测必需）

- **盘口数组不保证有序**：官方文档说 bids 降序、asks 升序，但实际可能把 0.99 的
  僵尸单放在 `asks[0]`，真实最优卖价 0.53 在中间。**按索引取价会读到最差价格。**
  V6 一律用 `max()/min()` 推导最优价（`Book.best_bid/best_ask`），并检测"交叉盘口"。
- **价格和数量是字符串**（`"0.48"` / `"1000"`），不是数字。
- **速率限制**（每 10 秒）：`/book` 1500 次，`/books` 500 次，CLOB 总计 9000 次。
  **超限是排队（增加延迟）而不是报错** —— 这会悄悄破坏对延迟敏感的逻辑。已记录在
  `RATE_LIMITS`。

## 四、问题 2：回测绩效体系 —— 已修复

V4 只打印"每份收益"和天数，**没有胜率、没有盈亏比、没有回撤、没有资金曲线**。
而且它打印的两种口径在**同一份数据上符号相反**（池化 −0.54% vs 逐日均值 −0.24%），
没有任何说明。

V6 用 `engine_v6/metrics.py` 从**同一份成交记录**算出全部指标：

```
  trades                : 1,138   over 22 days
  trades per day        : 51.7
  win rate              : 90.60%   (1031 wins / 107 losses)
  profit factor         : 0.885
  expectancy per trade  : -0.1091 USDC
  edge per share        : -0.836%
  mean entry price      : 0.9087
  total P&L             : -124.17 USDC
  return on stake       : -1.09%
  --------------------------------------------------------------------------
  MAX DRAWDOWN          : 164.85 USDC   (468.9% of peak)
  sharpe (per trade)    : -0.0335
  sortino (per trade)   : -0.0353
  positive days         : 7/22
  equity curve          : ▁▂▃▄▅▆▇█...
  --------------------------------------------------------------------------
  CAVEATS:
    - max drawdown is 468% of the peak cumulative P&L: the path is far rougher...
```

**关键设计**：`None` 表示"无法计算"，**永远不用 0 代替**。例如没有亏损时盈亏比是
`None` 而不是 0 或无穷大：

```
  [ok] profit factor undefined with no losses  (None)
  [ok] the undefined case is flagged as a caveat
```

任何指标异常都会自动生成 **CAVEATS**，样本太小、口径混杂、回撤过大都会明说。

`run_backtest_v6.py` 还输出**逐日分解**（每日笔数/胜率/盈亏/累计/回撤）和
**闸门漏斗**（每个闸门"到达多少 → 通过多少"），并支持
**样本内 / 样本外分列**。

## 五、最重要的发现：差别全部来自入场时点

**这是本轮最关键的结论。**

我之前报告"V6 实测 −0.836%，V4 报告的 +4.96% 不可复现"。**定位完成：**
**差别不在实现，而在入场时点。**

同一份数据、同一个信号、同一套闸门，只改入场时点：

| 时点 | 平均进场价 | 胜率 | **打平需要** | **差距** | 每份收益 |
|---|---|---|---|---|---|
| **T-180** | 0.9004 | 89.65% | 90.66% | **−1.01 点** | **−0.995%** ❌ |
| **T-240** | 0.8685 | 89.74% | 87.65% | **+2.09 点** | **+2.117%** ✅ |

**胜率几乎一样（89.65% vs 89.74%），差的是进场价 3.2 分钱 —— 而这 3.2 分钱就是亏损与盈利的全部分界。**

### 为什么 V6 一开始是负的

**V6 默认用了 T-180**（沿用 V4 的扫描结论）。**而 T-180 正好坐在盈亏平衡线上** —— 那里四舍五入都能决定符号。V4 报告的 T-180 是 +4.93%/天，V6 实测是 −1.0%/share，两者都"对"，因为那个点上策略本来就没有余量。

按进场价分桶看得更清楚（T-180）：

| 进场价区间 | 笔数 | 胜率 | 每份收益 |
|---|---|---|---|
| 0.00–0.75 | 10 | 50.0% | **−24.38%** |
| 0.75–0.82 | 53 | 73.6% | −6.45% |
| 0.82–0.88 | 177 | 84.2% | −2.10% |
| 0.88–0.92 | 322 | 89.8% | −0.32% |
| 0.92–0.96 | 306 | 94.4% | +0.57% |
| 0.96–1.01 | 108 | 96.3% | −0.77% |

**便宜的不一定好** —— 0.75 以下的进场价胜率只有 50%，**这些是"便宜但错"的交易**。

**T-240 的修正结果（已设为默认）：**

| | 样本内 | **样本外** | 全样本 |
|---|---|---|---|
| 笔数 | 321 | **380** | 701 |
| 笔/天 | 14.6 | **17.3** | 15.9 |
| 胜率 | 90.03% | **89.74%** | 89.87% |
| **盈亏比** | 1.275 | **1.257** | 1.265 |
| **每份收益** | +2.401% | **+2.301%** | +2.347% |
| **最大回撤** | 50.46 USDC（45.8%） | **50.97 USDC（39.9%）** | 50.97（23.5%） |
| 逐日为正 | 13/22 | **15/22** | 28/44 |

**样本外为正、盈亏比 1.26、回撤可控、逐日胜率 68%。**

### 与 V4 报告数字的对照

| | V4 报告（T-240） | **V6 实测（T-240）** |
|---|---|---|
| 笔数 | 1,145 | 380（样本外）|
| 胜率 | 93.6% | **89.74%** |
| 平均进场价 | 0.880 | **0.8665** |
| 每份收益 | +4.96% | **+2.30%** |
| 逐日为正 | 21/22 | **15/22** |

**V4 把优势夸大了约一倍。** V6 的数字更低，但**是同一套引擎同时算出进场价、胜率、盈亏平衡和回撤的**，口径一致、可复算。

### 结论

> **V4 的 +4.96% 站不住；但 T-240 上的 +2.3% 站得住** —— 样本外、有盈亏比、有回撤、有逐日分布。
>
> **关键教训：这套策略的利润全部藏在入场价里，不在胜率里。** 胜率在 T-180 和 T-240 几乎相同，但进场价差 3.2 分钱。**任何让入场价变贵几分的实现差异，都会把它从盈利变成亏损。**

## 七、怎么用

### 1. 自检（不需要网络）

```bash
cd v6_src
python tools_v6/test_v6.py                 # 期望 75/75
python tools_v6/static_check.py --path .   # 期望 0 个未定义变量
```

### 2. 确认深度口径（**必须先做，在交易机器上**）

```bash
python tools_v6/depth_check.py --live
```

它会并排打印数据集参考值和实时实测值，并给出判定。**这一步决定 0.30 阈值是否有效。**

### 3. 回测（需要数据集）

```bash
python run_backtest_v6.py --horizons 5m
```

### 4. 实时纸面交易

```bash
python run_live_v6.py probe        # 先验证行情源
python run_live_v6.py run --stake 10
python run_live_v6.py report       # 胜率/盈亏比/回撤/延迟漂移
```

## 八、V6 修复的缺陷清单

| # | 缺陷 | 后果 | 修复 |
|---|---|---|---|
| 1 | 现货按"最后取到的值"用 | 闸门测量值失真 | `SpotTracker` 时间戳配对 |
| 2 | 开盘价记录晚 20 秒 | 所有差值被压缩，三闸门过度拒绝 | 窗口一开即记录 + 报告滞后 |
| 3 | 单循环轮询 ~2s | 错过测量窗口 | 独立线程 + 短睡眠命中 |
| 4 | 只记拒绝原因 | **无法诊断频率差距** | 闸门账本：记录所有测量值 + 漏斗 |
| 5 | 无胜率/盈亏比/回撤 | 无法评估 | `metrics.py` 完整体系 |
| 6 | 两种口径符号相反且无说明 | 误导 | 统一口径 + CAVEATS |
| 7 | 深度口径未定义 | **阈值含义不明** | 参数化 + 多口径记录 + `depth_check` |
| 8 | 盘口按索引取价 | 可能读到最差价格 | `max()/min()` 推导 + 交叉检测 |
| 9 | 字符串价格未显式处理 | 潜在类型错误 | 显式 `float()` 转换 |
| 10 | 速率限制未记录 | 排队增加延迟，静默破坏逻辑 | `RATE_LIMITS` 常量 |
| 11 | 回测本地算量再重复闸门 | **策略闸门静默失效** | 全部量传入 `strategy.evaluate` |

## 九、诚实的限制

1. **`feed.py` 从未在真实网络下运行过**（开发环境无外网）。`probe` 必须先跑。
2. **深度口径未实测**。文档说完整、数据集说 10 档，**必须用 `depth_check.py --live` 确认**。
3. **T-240 上的 +2.3%/份 已定位且可复现**（第五节）：样本外为正、盈亏比 1.26、
   最大回撤 40%、逐日 15/22。但 **V4 报告的 +4.96% 站不住**，实际约为其一半。
4. **策略余量极薄**：入场价差 3.2 分钱就决定盈亏。**不要改动入场时点或深度口径**，
   除非重新验证 —— 这是唯一真正的杠杆，也是唯一的风险点。
5. **实时深度口径仍未实测**（第三节）。数据集是前 10 档，实时接口文档称完整盘口，
   两者算出的失衡不是同一个量。必须先跑 depth_check.py --live。
